# Tasks — IdemEngine (v1.2)

Desglose ejecutable de `plan.md` v1.1 en tareas de < 30 min, ordenadas por dependencia, con sus RF/INV y criterio "Hecho cuando:" verificable. Criterios de aceptación en `spec.md` (§18) y `plan.md`. T1 es infraestructura sin RF y ya está cerrada.

## Fase 0 — Fundaciones
- [x] **T1 — Scaffolding** (sin RF, infraestructura) · `NestJS + TS5 + eslint/prettier + docker compose (postgres, redis)`. Depende de: —. _Hecho cuando:_ `docker compose up -d` deja postgres y redis "healthy" y `npm run start:dev` responde en `/health`.
- [x] **T2 — CommonModule: Zod + errores** (entrada de todos los RF; const. #5/#6) · Pipeline de validación, DTOs e interfaces explícitas y mapeo de errores normalizado. Depende de: T1. _Hecho cuando:_ una petición inválida devuelve `400` con cuerpo normalizado y hay un test unitario que lo prueba.

Depende de: T2. _Hecho cuando:_ los tests fijan el reloj y obtienen resultados deterministas de "ahora" y de la tz configurada.

## Fase 1 — Núcleo de idempotencia
- [x] **T4 — Hash canónico del payload** (RF-02, RF-03) · Util pura sobre el DTO validado por Zod que ignora orden y espacios y normaliza tipos. Depende de: T2. _Hecho cuando:_ los unit tests prueban igualdad bajo reordenamiento/espacios/tipos y detectan un cambio de monto como payload distinto.
- [x] **T5 — Store de idempotencia en Redis** (RF-01, RF-02, RF-03, RF-04, RF-05 · INV-05, INV-06) · Registro `idem:<key>` con TTL 24 h sin gracia y estados `PROCESSING|SETTLED` (payload hash, respuesta asentada y ref de Billing Intent). Depende de: T1. _Hecho cuando:_ la integración con Redis real escribe/lee el registro, respeta el TTL y conserva el estado.
- [x] **T6 — Guard de idempotencia** (RF-01, RF-02, RF-03, RF-04, RF-05 · INV-05, INV-06) · Valida key (presente, no vacía, ≤255), compara hash canónico, responde `400`/`409`/`423` y hace replay de la respuesta asentada; registra `PROCESSING` y asienta `SETTLED` tras commit. Depende de: T4, T5. _Hecho cuando:_ la integración cubre `400` sin key, `409` por mismatch, `423` en vuelo, duplicado asentado y expiración sin margen.
- [x] **T7 — Guard sobre una mutación real + concurrencia** (RF-06, RF-07 · INV-05) · Cablea el Guard a un `POST` y prueba N requests concurrentes same-key/same-payload y same-key/different-payload. Depende de: T6. _Hecho cuando:_ N concurrentes producen 1 operación y 0 cobros duplicados, y el caso de payload distinto termina con exactamente una operación aceptada y un `409`.

- [x] **T8 — Migración `subscriptions`** (RF-08, RF-10 · INV-08, INV-09) · Tabla con `amount`, `currency`, `frequency`, `anchor_date`, `timezone`, `status` (`ACTIVE|PAUSED|CANCELLED`) y `cancelled_at`. Depende de: T2. _Hecho cuando:_ la migración aplica, es reproducible desde cero y los tests de constraints/estados pasan.
- [x] **T9 — Alta de suscripción** (RF-08) · `POST` validado por Zod: monto y divisa fijos, `startDate` válida según el reloj oficial. Depende de: T3, T8. _Hecho cuando:_ un alta válida responde `201` y una fecha no permitida, monto o divisa inválidos responden `400`.
- [x] **T10 — Migración `billing_intents` + `payment_attempts`** (RF-11, RF-12, RF-13, RF-14, RF-19, RF-29 · INV-01, INV-02, INV-03, INV-04, INV-10) · Identidad `(subscription_id, billing_cycle)`, estados de intent y attempt y `provider_operation_id`; constraints: `UNIQUE(subscription_id, billing_cycle)`, único parcial de intent vivo, `UNIQUE(intent, attempt_no)` + `CHECK attempt_no 1..5`, `UNIQUE(provider_operation_id)` y único parcial de attempt `IN_FLIGHT`. Depende de: T8. _Hecho cuando:_ la migración aplica y los tests de cada constraint fallan correctamente al violarlo.
- [x] **T11 — Consulta de suscripción e historial** (RF-09) · `GET` con estado, próxima facturación e historial de Billing Intents y Payment Attempts con estados finales y motivos de fallo. Depende de: T9, T10. _Hecho cuando:_ el `GET` devuelve estado, próxima fecha e historial completo con sus estados.
- [x] **T12 — Cancelación de suscripción** (RF-10, RF-28 · INV-08) · Mutación con key: no genera nuevas intenciones, detiene retries y marca como `OMITTED`/canceladas las no iniciadas; un attempt `IN_FLIGHT` puede terminar y su resultado se conserva. Depende de: T11. _Hecho cuando:_ tras cancelar no hay nuevas intenciones, las pendientes quedan no ejecutables y un `IN_FLIGHT` previo conserva su resultado.

## Fase 3 — Gateway y executor
- [x] **T13 — GatewayModule + MockPaymentAdapter** (RF-15, RF-20) · Contrato `IPaymentGateway` y mock con modos `SUCCESS`, `DECLINED`, `TIMEOUT`, `AMBIGUOUS` y `PROVIDER_ERROR`. Depende de: T2. _Hecho cuando:_ cada modo devuelve el resultado esperado y un test unitario lo prueba.
- [x] **T14 — Identidad de operación del provider + verify** (RF-15, RF-17 · INV-04) · `providerOperationId` estable por attempt y operación `verify(providerOperationId)` que reporta `SUCCEEDED|FAILED|UNKNOWN`. Depende de: T13. _Hecho cuando:_ dos `charge` con el mismo `providerOperationId` producen a lo sumo un cobro efectivo y `verify` reporta el estado real.
- [x] **T15 — Clasificación explícita de errores** (RF-19, RF-20) · Catálogo de reintentables (`TIMEOUT`, `PROVIDER_ERROR`, `TEMPORARY_UNAVAILABLE`) y no reintentables (`DECLINED`, `INVALID_PAYMENT`, `INVALID_AMOUNT`, `CANCELLED_SUBSCRIPTION`). Depende de: T13. _Hecho cuando:_ los unit tests garantizan que cada error del mock se clasifica de forma explícita.
- [x] **T16 — ChargeExecutor: exclusividad de ejecución** (RF-12, RF-13 · INV-01, INV-03) · Toma `SCHEDULED`→`IN_FLIGHT` con `SELECT … FOR UPDATE`, impide un segundo attempt simultáneo y registra el attempt con su `providerOperationId`. Depende de: T10, T13. _Hecho cuando:_ ante dos transacciones simultáneas sobre el mismo intent solo una avanza y la otra es rechazada o diferida.
- [x] **T17 — Confirmación verificada y estados terminales** (RF-15 · INV-06, INV-07) · Solo marca `SUCCEEDED` con confirmación verificable, persiste el resultado del attempt y nunca revierte `SUCCEEDED`. Depende de: T14, T16. _Hecho cuando:_ una respuesta local sin confirmación no asienta éxito y un intent `SUCCEEDED` no vuelve a ejecutar el adapter.
- [x] **T18 — Interrupción y UNKNOWN** (RF-16) · Si el worker pierde contacto, intent y attempt quedan `UNKNOWN`; un proceso de recuperación materializa la interrupción al expirar el timeout, con la información persistida en PostgreSQL. Depende de: T17. _Hecho cuando:_ matar el worker entre registro y respuesta deja `UNKNOWN` y la recuperación lo materializa al expirar el timeout.

## Fase 4 — Calendario y scheduling
- [x] **T19 — CalendarModule** (RF-23, RF-24, RF-25) · Días no hábiles configurables, tz única, siguiente día hábil (incl. cruce de mes) y truncamiento de fin de mes/año. Depende de: T3, T8. _Hecho cuando:_ los unit tests de hábil/no hábil, cruce de mes, `31→28/29` y 29-feb pasan.
- [ ] **T20 — Scheduler de ciclos desde el ancla** (RF-11, RF-23, RF-30 · INV-02) · Identifica el ciclo cuyo momento de procesamiento llegó y crea la Billing Intent de forma idempotente desde la fecha de anclaje, sin drift. Depende de: T10, T19. _Hecho cuando:_ las próximas fechas calculadas coinciden con el ancla y el despacho repetido no crea intents duplicadas.
- [ ] **T21 — Omitido y motor caído** (RF-18, RF-26, RF-31) · Los ciclos no procesables por indisponibilidad o por suscripción `PAUSED`/`CANCELLED` se registran `OMITTED` sin efectos económicos y sin catch-up. Depende de: T20. _Hecho cuando:_ con el motor detenido dos ciclos quedan `OMITTED` y el siguiente ciclo se calcula desde el calendario original.
- [ ] **T22 — No solapamiento de ciclos** (RF-14 · INV-01) · Mientras exista una intención viva (`SCHEDULED`/`IN_FLIGHT`/`UNKNOWN` o retry pendiente) no se inicia el ciclo siguiente. Depende de: T20. _Hecho cuando:_ con un ciclo en retry pendiente el siguiente no se inicia hasta que el anterior deje de estar vivo.
- [ ] **T23 — Calendario aplicado al procesar (fin de mes + hábil)** (RF-24, RF-25) · Aplica primero el truncamiento a último día del mes destino y después el desplazamiento a día hábil, sin mover el ancla. Depende de: T19, T21. _Hecho cuando:_ el e2e cubre anclaje día 31 → último día del mes destino → día hábil, y 29-feb anual en año no bisiesto.

## Fase 5 — Reintentos y outbox
- [ ] **T24 — Verificación de UNKNOWN antes de re-ejecutar** (RF-17 · INV-04, INV-07) · Consulta `verify(providerOperationId)`: `SUCCEEDED` cierra el cobro, `FAILED` permite un nuevo attempt y `UNKNOWN` mantiene el estado sin ejecutar. Depende de: T18. _Hecho cuando:_ la integración demuestra que un intent `UNKNOWN` no vuelve a llamar al adapter mientras `verify` devuelva `UNKNOWN`.
- [ ] **T25 — RetryScheduler con BullMQ** (RF-19, RF-20, RF-21 · INV-10) · Cola `charges.retry` que crea nuevos attempts sobre la misma Billing Intent con backoff `10 s·2ⁿ` + jitter ±20 %, tope 1 h, máximo 5, sin pasar por el dedupe externo ni crear nueva key. Depende de: T15, T17. _Hecho cuando:_ la cola programa ≤5 intentos con delays dentro de rango y no crea una nueva Billing Intent ni una nueva operación idempotente.
- [ ] **T26 — Agotamiento y evento de cancelación** (RF-22, RF-28) · Al 5º attempt fallido: `FAILED_FINAL` + Subscription `CANCELLED` + `CancellationEvent` persistido en la misma transacción. Depende de: T12, T25. _Hecho cuando:_ la integración agota los 5 intentos y persiste el evento junto con la cancelación de forma atómica.
- [ ] **T27 — Outbox consultable por API** (RF-22, RF-28) · Migración `notifications` y endpoint de consulta de eventos de dominio (sin transporte externo). Depende de: T26. _Hecho cuando:_ el `CancellationEvent` queda consultable por API tras la cancelación.

## Fase 6 — Operaciones administrativas
- [ ] **T28 — Admin: Pause** (RF-26 · INV-09) · Mutación idempotente con key que suspende nuevas intenciones y retries no iniciados y deja terminar el attempt `IN_FLIGHT`. Depende de: T22. _Hecho cuando:_ en `PAUSED` no se generan intenciones ni retries y un attempt en vuelo concluye.
- [ ] **T29 — Admin: Resume** (RF-27, RF-23) · Mutación idempotente con key que solo aplica `PAUSED`→`ACTIVE`, sin catch-up. Depende de: T28. _Hecho cuando:_ al reanudar, el siguiente cobro es el siguiente ciclo de calendario y no se recuperan fechas perdidas.
- [ ] **T30 — Admin: Cancel** (RF-28) · Cancelación idempotente por API con el mismo Guard y emisión del `CancellationEvent`. Depende de: T12, T27. _Hecho cuando:_ repetir la mutación no duplica efectos y el evento se persiste una sola vez.
- [ ] **T31 — Admin: Reprocess** (RF-29 · INV-02, INV-07) · Reprocesa `UNKNOWN`/`FAILED_FINAL` con un nuevo attempt sobre la misma intención, sin backoff automático y sin reactivar la suscripción; rechaza `SUCCEEDED`. Depende de: T24, T25. _Hecho cuando:_ el reproceso asienta sin duplicar ni crear una nueva intención y no se ejecuta sobre `SUCCEEDED`.
